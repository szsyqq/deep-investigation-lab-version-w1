01
FULL WORKFLOW

整体怎么使用

最推荐的入口仍然是自然语言。用户不需要操作七个技术关卡，只需要提出调查任务并在关键节点确认。

主体研究

“调查空客为什么订单创新高，交付和现金流却同时承压。”

话题研究

“调查新能源汽车价格战对供应商和消费者的实际影响。”

  1. 01 · 接收任务识别主体或话题研究，确认范围和反证条件。
  2. 02 · 讨论与研究讨论团提出读者问题；搜索、发现新问题并反复补充调查。
  3. 03 · 框架与底稿保存来源，形成论点、章节职责和报告框架。
  4. 04 · 文字初稿完成一篇以文字为主、前后连贯的完整文章。
  5. 05 · 视觉编辑从正文主张出发增加图表；不需要时保留纯文字。
  6. 06 · 审核与修改检查相似性、事实、结构，并自然融入分析师意见。
  7. 07 · 预览与发布先内部试读，明确批准后进入正式主页面。
关键原则

研究允许反复返回；图表必须在初稿和论点明确之后增加；内部试读不等于正式发布。

02
ANALYST REVISION

如何反复修改

分析师可以直接提疑问。系统先判断影响范围，再把修改重新组织进完整文章。

证据更新

先更新来源和事实，再修改受影响段落、数字和图表。

局部改写

保持章节职责不变，但重写段落并检查前后衔接。

结构调整

先修改报告框架和论点顺序，再重写章节与视觉计划。

全文重写

核心问题发生变化时，重新进入讨论和研究阶段。

新增调查

补同行、历史或反方资料后，重新判断原结论是否成立。

分析师确认

记录接受、修改或拒绝，不能只依赖聊天记忆。

可以直接这样提意见

  • “这个判断的证据够不够？请补充反方资料。”
  • “新增内容像硬插入，请重新组织这一章。”
  • “图表只重复正文，请重新判断是否需要可视化。”
  • “我同意这一版，进入内部试读。”
03
REPORT DOSSIER

每篇报告怎么维护

每篇报告拥有自己的底稿目录；网站框架共享，研究内容相互隔离。

研究

问题与来源

research-notes.md
sources/
evidence-ledger.json

写作

框架与成稿

outline.md
draft.md
visual-plan.json

治理

审核与发布

review.md
revisions.md
workflow-state.json
publication.json

用户意见→判断修改范围→更新底稿→重组完整文章→重新审核
  • 文章事实不在网页组件中直接维护。
  • 新报告不复制导航、样式和网站框架。
  • 修改当前报告不得改动其他报告。
  • 一次人工意见不会自动改写全局规则。
04
COMMANDS & ROADMAP

指令与后续开发

创建调查npm run research:new -- "调查主题"识别研究路线并创建完整底稿目录
推进阶段npm run research:advance -- <slug> --to=drafting更新报告生产阶段
内部试读npm run research:advance -- <slug> --to=internal-preview进入内部预览，不进入正式主页面
分析师批准npm run research:approve -- <slug> “确认意见”记录明确的人工批准
正式发布npm run research:advance -- <slug> --to=published分析师批准后更新正式发布状态
校验研究包npm run research:validate检查底稿、证据、状态和视觉引用
测试与构建npm test && npm run build验证系统规则与网站产物

近期02

证据采集助手

自动保存网页、文件、发布时间、摘要和冲突提示。

中期03

分析师审阅台

支持评论、疑问、修改范围判断、版本比较和逐项确认。

中期04

内部试读区

展示试读标签、未解决问题、负责人和审批状态。

后期05

经验治理

从重复人工决策中提出规则更新建议，但必须人工批准。

当前优先事项

先把一篇真实报告完整走通

从讨论、迭代研究和初稿开始，经过多轮分析师修改，再进入内部试读。闭环稳定后再迁移旧报告。
